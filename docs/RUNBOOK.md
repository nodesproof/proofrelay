# ProofRelay runbook

Operating the system, and what to do when a part of it fails.

## Health

```bash
curl -s localhost:8080/health | jq
```

```jsonc
{
  "ok": true,
  "chainId": 16602,
  "contract": "0x…",
  "drivers": {"storage": "zerog", "compute": "zerog-router"},
  "dependencies": {
    "database": {"ok": true},
    "storage":  {"ok": true, "detail": "…-turbo.0g.ai -> HTTP 200"},
    "compute":  {"ok": true, "detail": "…router-api.0g.ai/v1 -> HTTP 200"},
    "chain":    {"ok": true, "detail": "head=1234567"}
  },
  "indexer": {"running": true, "lastError": null, "processedEvents": 42},
  "queue":   {"PENDING": 0, "DONE": 17}
}
```

`/health` returns 503 when any dependency is down. `/health/live` never touches a
dependency and is the right liveness probe.

Metrics are on `/metrics` in Prometheus text format: `task_created_total`,
`task_completed_total`, `verifier_commit_total`, `verifier_reveal_total`,
`dispute_opened_total`, `payout_total`, `job_retry_total`,
`chain_sync_lag_blocks`, `compute_request_latency_ms`,
`storage_upload_latency_ms`, `http_request_latency_ms`.

## Alert thresholds (architecture doc §17)

| Alert | Condition | First action |
|---|---|---|
| Chain RPC down | `dependencies.chain.ok == false` | Switch `OG_RPC_URL` to a production provider |
| Indexer lag | `chain_sync_lag_blocks > 20` | Check `indexer.lastError`; `POST /v1/tasks/{id}/sync` to force a pass |
| Compute errors | `job_retry_total` rising, `compute.ok == false` | Check the ledger balance; consider `COMPUTE_DRIVER=local` to keep the demo alive |
| Storage errors | `storage.ok == false` | Check the storage wallet balance and the indexer endpoint |
| Queue backlog | `queue.PENDING` climbing | Check for `FAILED_FINAL` jobs; look at `last_error_code` in `jobs` |
| Contract underfunded | `address(contract).balance < totalLiabilities()` | Should be impossible; treat as a P0 contract bug |

## "It is running on the wrong chain"

Almost always a stale `.env.local`. It is generated by `npm run seed` and
`npm run demo`, and the services read it **ahead of** `.env`, so a file left
over from a local demo silently keeps everything on chain 31337.

```bash
grep -E 'CHAIN_ID|PROOFRELAY_ADDRESS' .env.local   # what the services actually use
curl -s localhost:8080/health | jq '{chainId, contract, drivers}'
```

Delete `.env.local` and re-run `npm run seed` to regenerate it for the intended
chain. Note that `npm run demo` is **destructive to a testnet setup**: it
rewrites `.env.local` onto a local anvil chain.

If the API is on the right chain but the **browser** looks wrong, it is the
wallet, not the deployment. The header names the network your wallet is on; a
banner appears when it differs from the API's. wagmi persists the last
connection, so a wallet left on Anvil stays selected across reloads — use
Disconnect in the header, or switch networks in the wallet itself.

## Common situations

### The read model disagrees with the chain

The UI shows `SYNC_REQUIRED` and displays the chain value. The chain is always
authoritative.

```bash
curl -X POST localhost:8080/v1/tasks/0x<taskId>/sync
```

To rebuild the whole read model, truncate it and let the indexer replay from
block 0. Nothing canonical lives in Postgres.

```sql
TRUNCATE chain_events, tasks, reports, consensus_results, disputes, jobs CASCADE;
DELETE FROM indexer_state;
```

### The keeper is offline and a task is stuck in `Revealing`

Nothing is trapped. Once `block.timestamp > revealDeadline` — the deployed
contract adds no grace period, whatever the `params()` field named
`keeperGracePeriod` is for — anyone can call:

```bash
cast send $PROOFRELAY_ADDRESS "expireTask(bytes32)" 0x<taskId> \
  --rpc-url $OG_RPC_URL --private-key $ANY_KEY
```

Verifiers that revealed are paid the conflict rate; the rest returns to the
creator.

### A task is stuck in `Consensus` after the dispute window

`finalizeTask` is permissionless:

```bash
cast send $PROOFRELAY_ADDRESS "finalizeTask(bytes32)" 0x<taskId> \
  --rpc-url $OG_RPC_URL --private-key $ANY_KEY
```

`claimReward` also auto-finalizes, so a verifier claiming their reward resolves
this on its own.

### A dispute was opened and no adjudicator acted

After `adjudicationWindow` (7 days by default) anyone can call `expireDispute`.
The bond is returned in full and the original consensus allocation stands.

### 0G Compute is failing

Each call retries three times with exponential backoff, then the job becomes
`FAILED_RETRYABLE` and eventually `FAILED_FINAL`. A task is **never**
auto-verified on compute failure. To finish a demo while the provider is down,
set `COMPUTE_DRIVER=local` and restart the workers: the deterministic engine
produces the same interface and the trace records which driver ran.

Check the driver actually in use:

```bash
curl -s localhost:8080/health | jq '.drivers'
```

### 0G Storage is failing

Uploads retry with backoff. Reads fall back to configured alternate gateways,
then to the API's indexed copy — and `/v1/reports/{hash}` marks the response
`"source": "cache"` when that happens. A **hash mismatch** is never served from
cache: it returns 409 `CONTENT_HASH_MISMATCH`, because that is exactly the
condition the hash exists to detect.

### A verifier missed its reveal window

The commitment stays unrevealed and that verifier earns nothing. If enough
verifiers revealed, consensus proceeds without it. If none did, `expireTask`
refunds the creator in full.

### Emergency stop

```bash
cast send $PROOFRELAY_ADDRESS "pause()" --rpc-url $OG_RPC_URL --private-key $ADMIN_KEY
```

Pause blocks new escrow, commitments and challenges. It deliberately does **not**
block finalization, expiry, or withdrawals — escrow can never be trapped by an
admin action.

## Backups and recovery

Canonical state is the chain plus 0G Storage. Postgres is an index and a job
coordinator and can be rebuilt from chain events at any time. Back it up daily
for convenience, but never make recovery depend on it.

What a full rebuild needs:

1. The contract address and chain ID.
2. An RPC that can serve logs from the deployment block.
3. 0G Storage reachable for the pointers recorded in those events.

## Key rotation

```bash
# grant the new keeper, then revoke the old one
cast send $PROOFRELAY_ADDRESS "grantRole(bytes32,address)" \
  $(cast keccak "PROOFRELAY_KEEPER") $NEW_KEEPER --private-key $ADMIN_KEY --rpc-url $OG_RPC_URL
cast send $PROOFRELAY_ADDRESS "revokeRole(bytes32,address)" \
  $(cast keccak "PROOFRELAY_KEEPER") $OLD_KEEPER --private-key $ADMIN_KEY --rpc-url $OG_RPC_URL
```

Verifier keys cannot be rotated mid-task: a commitment is bound to the address
that made it. Deactivate the verifier (`setVerifierActive(false)`), let its open
tasks settle, then register the new address.

## Demo checklist

1. `curl -s localhost:8080/health | jq '.ok'` → `true`
2. Register lists the seeded tasks with their statuses
3. Open the conflict task; the concordance band is visibly split
4. Both verifiers' quoted spans are visible with their source hashes
5. Copy a report hash; `GET /v1/reports/{hash}` returns `"verified": true`
6. The consensus transaction resolves on the explorer
7. Withdraw a reward and watch the balance move
